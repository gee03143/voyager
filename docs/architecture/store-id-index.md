# 스토어의 id 색인

`scripts/data/journal.gd`, `scripts/data/gratitude.gd`, `scripts/data/mood.gd`

## 역할

- id로 항목을 찾는 스토어는 배열과 함께 `id → 항목` Dictionary를 든다
- 값은 배열에 든 것과 **같은 참조**다. 사본이 아니라 같은 것을 두 곳에서 가리킨다
- 저장 포맷에는 나가지 않는다. `to_dict`는 배열만 넘긴다

## 계약

- 색인을 만드는 곳은 `from_dict` 하나다. 불러오기가 끝나면 `_reindex()`가 다시 짠다
- 색인을 고치는 곳은 `add_*` / `remove_*` 둘뿐이다. `update_*`는 id를 안 바꾸므로 읽기만 한다
- `IdGen.fresh()`에 색인을 그대로 넘긴다. 색인의 키 집합이 곧 사용 중인 id다
- 지우기는 배열에서 자리를 찾느라 여전히 훑는다. 드문 조작이라 그대로 뒀다
- 날짜로 찾는 것(`entry_for_date`)은 색인을 안 쓴다. 색인은 id 전용이다

## 주의

- ⚠️ **배열을 바깥에서 고치면 색인이 어긋난다.** `docs`·`entries`가 `var`로 열려 있지만 통째로 갈아끼우거나 직접 `append`·`remove_at` 하면 안 된다
  - 지금은 바깥에서 읽기만 한다(6곳). 쓰는 곳은 스토어 자신뿐이다
  - 합성 데이터로 시험할 때도 배열에 직접 넣지 말고 `from_dict`를 쓴다
- 왜 필요했는지: `Save.is_orphan_event()`가 이벤트마다 이 스토어들을 훑었다
  - 이벤트 수와 항목 수가 둘 다 사용 기간에 비례해 늘어 비용이 **제곱**이 됐다
  - 기록 달력을 열 때와 날짜를 고를 때, 컴패니언이 오늘을 셀 때 걸린다
- 실측(하루 뽀모도로 4 + 할 일 3 + 감사 1 + 무드 1, 일지 주 1회 기준)

  | | 1년 | 2년 | 3년 |
  |---|---|---|---|
  | `_recount` 색인 전 | 11.9 ms | 47.6 ms | 107 ms |
  | `_recount` 색인 후 | 2.3 ms | 4.7 ms | 10.1 ms |
  | `activity_entries_for` 색인 전 | 25.6 ms | 72.1 ms | 143 ms |
  | `activity_entries_for` 색인 후 | 16.2 ms | 28.6 ms | 44.9 ms |

- `activity_entries_for`에 남은 비용은 색인이 아니라 이벤트마다 부르는 날짜 변환이다. 그건 이벤트 수에만 비례하므로 제곱이 아니다
- 새 스토어에 id 조회가 생기면 같은 형태를 따른다. 조회가 없으면 색인도 두지 않는다
